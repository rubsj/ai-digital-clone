# ADR-018: Deterministic Routing; Explanation Belongs to the Consumer

**Status:** Accepted

**Date:** 2026-06-01

**Supersedes:** ADR-010 (GatekeeperAgent routing). ADR-010 remains as the Day-10 record of the original decision and is not edited.

## Context

The Day 12 ship/no-ship gate failed at 0 of 14 in-domain delivery on both leaders. Investigation peeled three stacked defects in the evaluation-and-routing layer (ADR-017 and its Amendment 1 fixed the first two: LLM-raised flags and a miscalibrated style threshold). The third, RC-2, is the subject of this decision and was confirmed as an independent defect once the first two were removed.

RC-2 is not what ADR-017 hypothesized. The original hypothesis was that the GatekeeperAgent routes on flag presence. The re-evaluation with correct deterministic flags disproved that: of 25 fully flag-clean records, only 3 delivered and 22 fell back. The GatekeeperAgent was overriding clean flags and performing its own unconstrained LLM groundedness judgment. That judgment is non-monotonic in the score: a record scoring groundedness 0.675 delivered while records at 0.727, 0.715, and 0.698 fell back, so no single internal threshold explains the behavior. The same query and leader flipped deliver, fallback, deliver across three identical temperature-0 passes while its score barely moved. An LLM placed at a decision point that is fundamentally arithmetic fabricated nondeterminism. The arithmetically false reasoning strings (for example asserting 0.653 is below the 0.60 target) are the tell that the model was not reading the number at all; it was generating groundedness-skepticism prose and routing on it. The same mechanism produced RC-3 (fabricated trigger_category): the GatekeeperAgent labeled every fallback low_groundedness regardless of the actual flags, because its freehand judgment was always about groundedness.

This is the same class of error as RC-1, one level up. RC-1 was an LLM asked to compare two numbers and getting it wrong; the fix was to take the comparison away from the LLM. RC-2 is an LLM asked to route on already-computed flags and ignoring them; the same fix applies. Holding the GatekeeperAgent as an LLM decider while having just removed the EvaluatorAgent's LLM decision role would be two contradictory positions about where LLM judgment belongs.

A precondition check against the code (flow.py, groundedness_scorer.py) established the facts this decision depends on. A zero-chunk retrieval is not guarded upstream: it flows through retrieve, clone, and evaluate, producing a real EvaluationResult (the groundedness scorer returns 0.0 immediately on empty chunks, groundedness_scorer.py:56), so the evaluate-is-None emergency guard does not fire and the case reaches the router. A zero-chunk case is therefore indistinguishable from a genuinely low-groundedness case by score alone (both are below the 0.60 floor); the only discriminant is the chunk count at the router.

## Decision

Replace the GatekeeperAgent's LLM decision with a deterministic routing function, and move the explanation role to the consumer that actually uses it, the FallbackAgent.

Routing is deterministic, computed in three distinct steps that must not collapse. First, compute all three flags from the deterministic scores (groundedness, style, confidence), per the ADR-017 fix. Second, branch on groundedness only: fall back if and only if the low_groundedness flag is set, otherwise deliver. Groundedness is the sole delivery-blocking flag because it is the only one tied to the safety property; an ungrounded answer is a hallucination, whereas a grounded answer that is slightly off-voice or lower-confidence is still a true, sourced answer worth delivering. Third, attach all set flags to the result: blocking ones drive the fallback, non-blocking ones (low_style, low_confidence) travel with a delivered response as quality metadata.

The trigger_category is set by code, not generated, which eliminates RC-3 at the root. The router emits only the categories it can determine without judgment, a tree checked in order: empty_retrieval when the chunk count is zero (checked first, because a zero-chunk case also fails the groundedness floor and would otherwise mislabel as low_groundedness), then low_groundedness when chunks are present and groundedness is below the floor. The remaining three of the original five literals (off_domain, hallucination_risk, chunk_mismatch) require semantic judgment the code cannot make and are intentionally unreachable from the routing path. They remain in the schema for contract stability. This is a deliberate narrowing: the router labels only what it can know deterministically, rather than inventing labels for states it cannot distinguish.

A sixth literal, evaluation_error, is added for one further deterministically-knowable state: the evaluate step producing no result (evaluation is None). This is the same principle applied to an internal-failure case rather than a content case. The flow currently has an emergency guard on this path (flow.py) that constructs a fallback RoutingDecision with a null trigger_category, which violates the fallback-has-a-category contract; it has never fired because no record has produced a null evaluation. The decision is to degrade gracefully on internal failure: an evaluation failure routes to a user-facing fallback (the user sees a normal redirect, not an error), but it is labeled honestly as evaluation_error with a factual trigger_reason, so the internal failure is visible in logs and eval even though the user experience stays clean. The alternative, surfacing evaluation failure as a distinct error path rather than a fallback, was considered and rejected for this scope: it introduces a third flow outcome beyond deliver and fallback, a larger change than warranted, and graceful degradation with honest labeling preserves the user experience while keeping the failure observable. Adding evaluation_error is a deliberate, decision-recorded category for a real distinct state, which is the opposite of the LLM-invented categories RC-3 produced; the rule is not "five categories forever" but "code does not invent categories to rationalize judgment." The router's reachable trigger_category vocabulary is therefore the three-literal set {low_groundedness, empty_retrieval, evaluation_error}.

The trigger_reason is written by code as a factual templated string (the category and the actual score values), not LLM prose. The FallbackAgent then generates the rich, in-voice redirect from that factual reason plus the trigger_category, the scores, the retrieved chunk topics, and the leader's style profile. Code asserts the fact; the LLM dresses it for the human. The FallbackAgent is enriched to receive trigger_category and the scores (it previously received only a free-text reason), and its style_profile parameter, which was accepted but silently unused, is wired into the task description so the redirect is generated in the leader's voice rather than a generic apology. The GatekeeperAgent as an LLM agent dissolves; the language work it was never doing well moves to the agent whose job it actually is.

The delivered response carries non-blocking flags as quality metadata via a new RoutingDecision.quality_flags field, so a delivered-but-low-style response is auditable and a future deliver-with-a-note behavior is possible without re-architecting.

## Alternatives Considered

- Keep the GatekeeperAgent as an LLM and fix it with a better prompt (instruct it to compare numerically against 0.60). Rejected. The re-evaluation showed the failure is not a wrong threshold but the absence of any threshold; the LLM's decision is noise with respect to the score. Prompting an LLM to behave deterministically at a deterministic decision point is the error RC-1 already demonstrated, repeated.
- Keep the GatekeeperAgent as an LLM explainer that narrates a decision made by code (a decide-in-code, explain-in-LLM split inside the same agent). Rejected as redundant once the consumer was identified: the explanation's only real consumer is the FallbackAgent, which already exists and already generates human-facing prose. A separate explainer agent would duplicate that role. The delivered path needs no routing explanation (a clean response carries no "why I delivered it" note), so explanation is a fallback-path concern that belongs to the FallbackAgent.
- Make all three flags block delivery (the original intent of the broken behavior). Rejected. It conflates a quality issue (off-voice, lower-confidence) with a safety issue (ungrounded), and it is what produced the over-refusal. Style and confidence below target are quality metadata, not vetoes.
- Drop non-blocking flags on the delivered path rather than attaching them. Rejected for a small cost: attaching them as quality_flags preserves the audit trail and future deliver-with-a-note behavior for one nullable list field.

## Quantified Validation

- RC-2 is a confirmed independent defect, established only after RC-1 and the style threshold were fixed: 22 of 25 flag-clean records fell back under the LLM router, and routing was non-monotonic in groundedness (0.675 delivered; 0.727, 0.715, 0.698 fell back), with the same query flipping decision across three identical passes. No threshold reproduces this; only unconstrained LLM judgment does.
- The deterministic router is verifiable without API calls: a pure-function assertion over the 84 stored re-evaluation records confirms the router delivers if and only if groundedness is at or above 0.60.
- The router's live trigger_category vocabulary is the reachable set {low_groundedness, empty_retrieval, evaluation_error}, confirmed against the code path (zero-chunk retrieval reaches the router; scorer returns 0.0 on empty chunks, so chunk count is the only discriminant; evaluation is None is caught by the flow's emergency guard, now emitting evaluation_error). The integrity assertion is scoped to this reachable set and to router-produced-and-guard-produced fallback decisions, and must not fail on the three intentionally-unreachable literals being absent.
- The empty_retrieval and evaluation_error branches are unexercised by the stored eval data (zero zero-chunk records and zero null-evaluation records across all 130 pair-records), so their coverage comes from constructed unit cases (a zero-chunk input through the pure routing function, and an evaluation-is-None case through the guard), not from the eval set. This is recorded as a Day-13 eval-coverage gap.
- The fallback enrichment is validated separately from the deliver rate, which is structurally blind to prose quality: a fallback-quality read confirms the redirects are specific to the trigger_category and generated in the leader's voice (style_profile now wired), not the prior generic redirect.

## Consequences

The deliver/fallback decision now rests on arithmetic that cannot drift and cannot fabricate nondeterminism. The trigger_category is code-set, which removes RC-3. The FallbackAgent becomes meaningfully richer: it knows why the system declined and answers in the leader's voice, fixing a previously dead style_profile parameter. The agent count drops from four LLM agents to three; the Gatekeeper, now fully deterministic, is by the project's binary taxonomy (LLM-driven is an agent, deterministic is a component) a component, not an agent. It is renamed from GatekeeperAgent to Gatekeeper and relocated to the components location alongside the other deterministic building blocks (ScoringEngine, Retriever) in Phase 1.7, a behavior-preserving rename done after the re-evaluation clears, with the test suite green before and after. ADR-014's inventory moves it from the agent list to the component list accordingly. The concept name "gatekeeper" is kept because the gating function is unchanged; only its implementation and therefore its type changed. The narrative is stronger for it, because each remaining agent's LLM status now has a stated reason and the deterministic pieces are uniformly components. The GatekeeperAgent file is the only routing change; the flow's contract (run returns a RoutingDecision, the router step reads .decision) is unchanged, so flow.py and downstream code are untouched except for passing the new fields into the FallbackAgent.

The evaluate-is-None emergency guard in flow.py is brought into the contract: it previously constructed a fallback RoutingDecision with a null trigger_category (a contract violation), and now emits evaluation_error with a factual trigger_reason. It has never fired (no record has had a null evaluation), so it is covered by a constructed unit case rather than the eval set, and the 1.6.1 integrity assertion is scoped to include this guard-produced fallback alongside router-produced ones. Whether an internal evaluation failure should remain a graceful user-facing fallback or become a distinct error path is settled here as graceful-with-honest-labeling; revisiting it toward a separate error outcome would be a future decision, not a gap left open tonight.

This decision does not change ADR-004 (groundedness floor 0.60, calibrated) or ADR-017 Amendment 1 (style threshold 0.70). The groundedness-only-blocks rule uses those calibrated thresholds; it does not alter them. CONFIDENCE_MIN remains 0.80 and uncalibrated as a per-response floor, but under groundedness-only routing it no longer blocks delivery, so its calibration is deferred without cost. This ADR is the citation point for Phase 1.6 in docs/plans/day12-plan.md. (For a Java or TypeScript reader: this is removing a service that wrapped a hand-written judgment call and replacing it with a pure function returning the same typed result, while the human-readable message moves to the component that renders it to the user, the same separation as keeping business rules in a typed function and leaving presentation to the view layer.)
