# ADR-017: Deterministic Flag-Raising in the Evaluation Path

**Status:** Accepted

**Date:** 2026-06-01

## Context

The Day 12 ship/no-ship gate ran the v2 pipeline against the evaluation set under real LLMs for the first time. The in-domain deliver rate came in at 0 of 14 for both leaders, identical across all three passes (zero variance). The out-of-domain criteria passed: 6 of 6 fallback per leader, zero hallucinations. By ADR-015 the gate is conjunctive and clause (a) failed below both per-leader floors (Torvalds 42.9%, Kroah-Hartman 35.7%), so the pre-committed Risk Register outcome applies: no-ship, investigate, do not cascade a broken P6 into the review tail.

The failure is not where the pre-flight suggested. The Day 12 pre-flight had found that the CloneAgent adds short ungrounded "when to use this" tails to otherwise-grounded answers, and that finding is real. But it is not why the rate is zero. Reading the gate records against the source code establishes a different and more fundamental cause.

No step in the evaluation path performs a numerical threshold comparison. The three targets (style > 0.90, groundedness > 0.60, confidence > 0.80) exist only as f-string literals inside the EvaluatorAgent's natural-language task description (`evaluator_agent.py:71-85`). There is no `if score < threshold` anywhere in code. The flags that drive routing are produced by LLM judgment, twice: the CrewAI kickoff LLM writes a prose verdict referencing the scores, and a second LLM in `_parse_review` (`evaluator_agent.py:113-127`) extracts snake_case flag labels from that prose without re-reading any number. The EvaluatorAgent backstory instructs it to be "direct" and to "name concrete problems rather than hedging," which biases the reviewer toward raising flags. Conservative prose from the first LLM propagates into the structured flag list produced by the second.

The measured consequence: 13 of 28 in-domain records scored at or above the 0.60 groundedness target and were still flagged `low_groundedness`, including q08 Kroah-Hartman at 0.706, eleven points clear of the target. The GatekeeperAgent then routes on flag presence rather than score value. Its backstory says "default to deliver when no flags are raised," whose contrapositive ("flags present, fallback") governs in practice; it is never instructed to compare groundedness numerically against 0.60. Its reasoning strings confirm this, including an arithmetically false justification on q11 Kroah-Hartman: it states 0.651 is below the 0.60 threshold. The number is laundered into qualitative language at the first LLM hop and is gone by the routing decision. Because every one of the 96 records carried at least one flag, the GatekeeperAgent never received a flag-clean record, so its flag-coupling could not be observed in isolation.

## Decision

Move flag-raising out of LLM judgment and into deterministic code in the EvaluatorAgent. Each flag is raised if and only if the corresponding ScoringEngine score is below its threshold, with the three thresholds defined as named constants (groundedness 0.60, style 0.90, confidence 0.80). The LLM no longer decides flags; it produces only the explanation prose. The ScoringEngine already computes the numeric scores deterministically and correctly, so the comparison is pure arithmetic on values that exist.

The redundant `_parse_review` second LLM call is removed. Its sole purpose was extracting flags from the first LLM's prose; with flags now code-raised, it has no remaining job. The explanation is taken directly from the kickoff `.raw` text. This is guarded: before relying on the raw text, it is compared against the previously-parsed explanation on a small sample of records, and if `_parse_review` was meaningfully rewording rather than merely extracting, the explanation generation is kept and the parse removal is deferred so the re-evaluation isolates the flag change.

The GatekeeperAgent is deliberately not changed in this decision. The hypothesis that it routes on flag presence rather than score value (designated RC-2) is strongly evidenced by its reasoning strings but cannot be proven from the gate data, because no flag-clean record ever reached it. Fixing the flag logic produces flag-clean records for the first time. The GatekeeperAgent's behavior is then read off the re-evaluation: if a record scoring at or above 0.60 with no `low_groundedness` flag delivers, RC-2 was masked by the flag bug and is not independent; if such a record still falls back, RC-2 is a confirmed independent defect and is addressed as its own change with its own re-measurement. One fabricated `trigger_category` label observed on q14 Torvalds (designated RC-3, `low_groundedness` assigned when no `low_groundedness` flag was raised) shares the GatekeeperAgent's back-filling mechanism and is expected to resolve with RC-2 rather than separately.

## Alternatives Considered

- Prompt-tune the EvaluatorAgent to be less conservative. Rejected. This chases the same LLM-judgment behavior that produced the bug; it tunes prose to approximate arithmetic and can drift again under any model or wording change. A threshold comparison is deterministic and belongs in code, not in a backstory's tone.
- Fix the GatekeeperAgent routing prompt at the same time as the flag logic. Rejected for this change. RC-2 is unprovable until the flag bug is removed, and changing both at once means a recovered deliver rate cannot be attributed to either, leaving the routing defect possibly latent for the next legitimate flag. The flag fix is the single measured variable; the GatekeeperAgent read follows it.
- Add a code-level threshold validator on the live routing path. Rejected, consistent with the Day 11 decision (ADR-010): the router has no failsafe, so a hard validator on the live path converts mislabeled data into a crashed pipeline. The deterministic comparison belongs in the EvaluatorAgent where the flag originates, not as a guard bolted onto the GatekeeperAgent.
- Treat the low rate as a corpus or CloneAgent problem and tighten the clone prompt. Rejected by the evidence. Retrieval is strong (rank-0 above 0.75) on 7 of 14 in-domain queries and the clone responses are largely grounded; q08 Kroah-Hartman at 0.706 groundedness is a well-grounded answer that was refused. The binding constraint is the flag-and-route layer, not generation or retrieval.

## Quantified Validation

- The failure is deterministic, not stochastic: 0 of 14 in-domain delivery on both leaders across three passes with zero variance, so it is a logic defect rather than a sampling artifact.
- RC-1 is measured: 13 of 28 in-domain records scored at or above the 0.60 groundedness target and were still flagged `low_groundedness`, the highest being 0.706. A correctly functioning flag step would have raised zero `low_groundedness` flags on those 13 records.
- The fix is verified by a unit assertion that no record with groundedness at or above 0.60 carries a `low_groundedness` flag, checked across the re-evaluation records.
- The re-evaluation runs the in-domain set only (14 queries per leader, three passes). Out-of-domain is excluded because it already passed at 6 of 6 fallback with out-of-domain groundedness measured at 0.33 to 0.48, far below 0.60, so a flag-calibration change cannot flip an out-of-domain record to deliver. The eventual final gate re-run uses the full set.
- RC-2 is adjudicated by a defined post-fix observation: whether a flag-clean, at-or-above-0.60 record delivers. This is the measurement that distinguishes a masked dependency from an independent defect.

## Consequences

The deliver decision now rests on arithmetic that cannot drift, instead of on the tone of an LLM backstory. The flag step is no longer a source of silent regression, and removing the `_parse_review` call also removes one sequential LLM round-trip from a pipeline measured at roughly 54 seconds per pair, a latency benefit recorded as a Day-13 item rather than claimed here. The cost is that the EvaluatorAgent's explanation and its flags are now produced by different mechanisms (LLM prose, code comparison), so the explanation text can in principle describe a dimension as weak while the code does not flag it; this is acceptable because the flags, not the prose, drive routing. The original Phase 2 work (cli and visualization refactor, v1 retirement) stays blocked until the re-evaluation clears the floors and RC-2 is resolved. This ADR is the citation point for the Day 12 investigation and the Phase 1.5 fix in `docs/plans/day12-plan.md`; the GatekeeperAgent disposition (RC-2, RC-3) is recorded against the re-evaluation result, not pre-judged here. (For a Java or TypeScript reader: this is moving a threshold check out of a hand-written natural-language instruction and into a typed comparison against named constants, the same reason one would not ask a reviewer to eyeball whether `0.706 < 0.60` when `score < GROUNDEDNESS_MIN` is exact and testable.)
